## Fix Details

### 1. `.toFixed()` crash on shop screen

**Problem:** `product.originalPrice` arrives as a string from the API (e.g., `"150.00"`). Calling `.toFixed(2)` on a string throws `TypeError`, crashing the entire shop grid.

**Fix:** Wrapped all price expressions in `Number()` with `|| 0` fallbacks across 5 locations in the shop product card renderer:

```js
// Before (crashes if originalPrice is a string)
(product.originalPrice || ...).toFixed(2)

// After
Number(product.originalPrice || ...).toFixed(2)
```

**Files changed:** `app/(tabs)/shop.js` — lines 354, 356, 361, 367, 373

---

### 2. `.toFixed()` crash on favorites screen

**Problem:** `(product.displayPrice || product.price).toFixed(2)` — if `displayPrice` is `0` (falsy) and `price` is `undefined`, evaluates to `undefined.toFixed(2)` which crashes.

**Fix:** Same `Number()` + `|| 0` pattern applied to 3 price expressions.

**Files changed:** `app/favorites.js` — lines 271, 277, 285

---

### 3. Cart `addItem` state mutation + stale closure

**Problem:** Two bugs in one:

1. **Direct state mutation.** `[...items]` shallow-copies the array, but `newItems[existingItemIndex].quantity += quantity` mutates the original state object. React may not detect the change.
2. **Stale closure.** The existing-item path reads `items` from the closure and calls `setItems(newItems)` instead of a functional updater. Rapid "add to cart" taps read the same stale `items`, and the second call's `setItems` overwrites the first — losing the first item.

**Fix:** Converted to a single `setItems(prev => ...)` functional updater. Uses `prev.map()` to create a new object for the matched item (no mutation).

```js
setItems(prev => {
  const existingIdx = prev.findIndex(item => ...);
  if (existingIdx >= 0) {
    return prev.map((item, i) =>
      i === existingIdx ? { ...item, quantity: item.quantity + quantity } : item
    );
  }
  return [...prev, newItem];
});
```

**Files changed:** `contexts/CartContext.js` — `addItem` function

---

### 4. Cart `updateColor` stale closure

**Problem:** The merge-quantities path derived a new array from the closure `items` instead of using a functional updater. If any other cart operation ran between the render and this `setItems`, those changes were silently discarded.

**Fix:** Moved entire logic inside `setItems(prev => ...)`. Both the merge path (`prev.map().filter()`) and simple path (`prev.map()`) now operate on `prev`.

**Files changed:** `contexts/CartContext.js` — `updateColor` function

---

### 5. Favorites race condition

**Problem:** Both `addToFavorites` and `removeFromFavorites` read `favorites` from the closure, compute a new array, and call `setFavorites(newArray)`. Two rapid operations both see the same stale `favorites` — the second call overwrites the first. Lost items are also persisted to AsyncStorage.

**Fix:** Both functions now use `setFavorites(prev => ...)` to derive the updated array from the latest queued state:

```js
let updatedFavorites;
setFavorites(prev => {
  updatedFavorites = prev.filter(fav => fav.id !== productId);
  return updatedFavorites;
});
await saveFavorites(updatedFavorites);
```

**Files changed:** `contexts/FavoritesContext.js` — `addToFavorites`, `removeFromFavorites`

### 6. JWT leaked to unencrypted AsyncStorage (security)

**Problem:** `storeUserSession` correctly stripped the token from `profileData` and stored it in SecureStore (encrypted). But line 41 wrote the **original `userData` (with the token)** to the legacy AsyncStorage key. Additionally, `updateSecureToken` wrote the new token back into the legacy key. AsyncStorage is unencrypted on-device storage — on a rooted/jailbroken device, any app can read it.

Three leak paths were identified:
1. `storeUserSession` — legacy key write (line 41)
2. `storeUserSession` — fallback path (line 48)
3. `updateSecureToken` — legacy key update (line 146)

**Fix:**
- Legacy key now receives `profileData` (token already stripped)
- Fallback path creates a fresh copy and strips the token
- `updateSecureToken` actively removes the token from the legacy key

**Trade-off:** If SecureStore itself fails on the device, the token is not persisted (user must re-login). This is acceptable — leaking the JWT to plaintext storage was the security issue.

**Files changed:** `services/secureTokenStorage.js` — lines 41, 46-51, 144-149

### 7. Product fetch sends user ID without auth token (security)

**Problem:** The `fetchProducts` function used `if/else if` logic: when `user.id` exists (the common case for logged-in users), only the `x-user-id` header was sent — the `else if` meant the `Authorization` Bearer token was never included. Any client could impersonate any user by setting the `x-user-id` header.

**Fix:** Changed to two independent `if` blocks so both headers are always sent together:

```js
// Before
if (user?.id) {
  headers['x-user-id'] = user.id;
} else if (user?.token) {
  headers['Authorization'] = `Bearer ${user.token}`;
}

// After
if (user?.token) {
  headers['Authorization'] = `Bearer ${user.token}`;
}
if (user?.id) {
  headers['x-user-id'] = user.id;
}
```

**Files changed:** `services/api.js` — `fetchProducts` headers

### 8. Double-submit protection on checkout

**Problem:** The only guard against double-submission was `setIsProcessing(true)` + `disabled={isProcessing}` on the button. Since `setIsProcessing` is a React state update, there's a frame gap between the tap event and the next render where `disabled` takes effect. A fast double-tap could invoke `handleSubmit` twice, creating duplicate orders.

**Fix:** Added a `useRef`-based guard that fires synchronously (no frame gap):

```js
const submittingRef = useRef(false);

const handleSubmit = async () => {
  if (submittingRef.current) return;
  submittingRef.current = true;
  // ... validation, submission ...
  // Reset in finally block and on validation-error early return
};
```

**Files changed:** `app/checkout.js` — `submittingRef` declaration, `handleSubmit` guard, validation early return, finally block

### 9. Card orders missing customer fields

**Problem:** `submitCODOrder` sent `customerName`, `customerEmail`, `customerPhone`, `customerAddress` as both top-level fields and nested in a `customer` object. `submitCardOrder` only sent them nested inside `customer`, and omitted `paymentMethod`. If the backend reads top-level fields for email templates or admin display, card orders would be missing customer contact info.

**Fix:** Added top-level customer fields, `emirate` inside the `customer` object, and `paymentMethod: 'card'` to match the COD payload structure.

**Files changed:** `services/orderService.js` — `submitCardOrder` payload

---

### 10. Empty address ID deletes all addresses

**Problem:** If `addressId` is `undefined`, `null`, or empty string (and not `'legacy'`/`'primary'`), the `id` variable becomes `''` after `String(addressId || '').trim()`. The falsy check `id ?` evaluates to `false`, so the endpoint becomes `/user/addresses` (the collection) — a DELETE that could wipe all of the user's saved addresses.

**Fix:** Added an early return with an error when `id` is empty:

```js
if (!id) {
  log.warn('deleteAddress called without an address ID');
  return { success: false, error: 'Address ID is required' };
}
```

**Files changed:** `services/databaseService.js` — `deleteAddress` function

---

### 11. `registerUser` crashes on non-JSON error responses

**Problem:** `response.json()` throws if the server returns HTML (500 page), plain text, or any non-JSON response. The exception falls into the outer catch which reports "Network error" — misleading and unhelpful.

**Fix:** Changed to read `response.text()` first, then attempt `JSON.parse` in a try-catch. Matches the defensive pattern used in `submitCODOrder` and other error handlers in the codebase.

```js
const errorText = await response.text();
let errorData = {};
try { errorData = errorText ? JSON.parse(errorText) : {}; } catch {}
```

**Files changed:** `services/authService.js` — `registerUser` error branch

## Issues Investigated But Not Bugs

| Issue | Verdict |
|-------|---------|
| Push token never registered in NotificationContext | Not a bug — registration is opt-in via profile.js toggle, which calls `registerForPushNotificationsAsync()` and `savePushTokenToBackend()`. The `expoPushToken` in NotificationContext is unused dead state. |
| `aps-environment = development` in entitlements | Cosmetic — EAS Build provisioning profile overrides this during code signing. |
| `LSMinimumSystemVersion = 12.0` in Info.plist | Non-issue — `LSMinimumSystemVersion` is a macOS-only key, ignored on iOS. Deployment target is controlled by `IPHONEOS_DEPLOYMENT_TARGET = 15.1`. |
| Apple Pay entitlements drift (`app.json` vs `.entitlements`) | Expected — EAS Build runs `expo prebuild` which regenerates the native project from `app.json`. The committed `ios/` folder is a stale snapshot. |
| Deep-link delegate ordering in AppDelegate.swift | Standard Expo SDK 52+ template. The asymmetry between `open url` and `continue userActivity` is intentional (restorationHandler semantics). |
