## Fix Details

### 1. `renderCartItem` useCallback has stale deps (HIGH)

**Problem:** `handleQuantityChange` and `handleRemoveItem` were plain arrow functions (not memoized). Since `renderCartItem` listed them in its `useCallback` dependency array, a new function reference was created every render, defeating the memoization entirely. This caused the entire FlatList to re-render on every state change.

**Fix:** Wrapped both handlers in `useCallback`:

```js
// Before
const handleQuantityChange = (item, change) => { ... };
const handleRemoveItem = (item) => { ... };

// After
const handleQuantityChange = useCallback((item, change) => {
  const newQuantity = item.quantity + change;
  updateQuantity(item.product.id, newQuantity, item.selectedColor, item.selectedSize);
}, [updateQuantity]);

const handleRemoveItem = useCallback((item) => {
  removeItem(item.product.id, item.selectedColor, item.selectedSize);
}, [removeItem]);
```

Also updated the `renderCartItem` dependency array to include the actual used references (`updateColor`, `updateSize`, `isRTL`) instead of stale ones (`getCategoryTranslationKey`, `isPromoItem`).

**File changed:** `app/(tabs)/bag.js`

### 2. Promo `useEffect` potential infinite loop (HIGH)

**Problem:** The free mask promotion `useEffect` depended on `items` in its dependency array, but it also called `setItems()` inside the effect body. Even though there was a bail-out check (`if (same) return prev`), the bail-out compared items by reference in a shallow loop that could miss edge cases, and the effect was still triggered on every `items` change regardless.

**Fix:** Replaced the `items` dependency with a tick-based trigger system:

1. Added `promoTick` state and `bumpPromoTick()` callback
2. Every cart mutation (`addItem`, `removeItem`, `updateQuantity`, `updateColor`, `updateSize`, `clearCart`) now calls `bumpPromoTick()` after modifying items
3. The promo `useEffect` depends on `[promoTick, user, selectedEmirate, emirates, shippingRates, isLoading]` — never on `items` directly
4. Subtotal calculation moved inside the `setItems` updater where it reads `prev` (the true current state)

```js
// Before — items triggers itself
useEffect(() => {
  const nonPromoItems = items.filter(...);
  const subtotal = ...;
  setItems(prev => { ... });
}, [items, user, selectedEmirate, ...]);

// After — tick triggers, reads prev inside updater
useEffect(() => {
  if (isLoading) return;
  setItems((prev) => {
    const prevNonPromo = prev.filter(...);
    const totals = calculateCartTotals(prevNonPromo, ...);
    // ... compute desired promos from prev ...
  });
}, [promoTick, user, selectedEmirate, emirates, shippingRates, isLoading]);
```

Also added `itemsRef` (synced on every render) for any future code that needs to read items outside of updaters without triggering effects.

**File changed:** `contexts/CartContext.js`

### 3. Race condition in `addToFavorites` / `removeFromFavorites` (HIGH)

**Problem:** Both functions used a pattern where `updatedFavorites` was assigned inside a `setFavorites` updater callback, then read after the `setFavorites` call. In React 18 with automatic batching, the updater may not execute synchronously in async contexts, meaning `updatedFavorites` could still be `undefined` when the code tries to save it to storage.

The `addToFavorites` function also compared `updatedFavorites === favorites` using the stale outer closure `favorites` instead of the `prev` from the updater, which could return a false positive under rapid calls.

**Fix:**

1. Used a boolean flag (`alreadyExists`) set inside the updater to track the outcome
2. Added `await Promise.resolve()` after `setFavorites` to yield a microtask, ensuring the updater has executed before reading the flags
3. Removed the stale `favorites` reference comparison

```js
// Before — race condition
let updatedFavorites;
setFavorites(prev => {
  if (prev.some(fav => fav.id === product.id)) {
    updatedFavorites = prev;
    return prev;
  }
  updatedFavorites = [...prev, newFavorite];
  return updatedFavorites;
});
if (!updatedFavorites || updatedFavorites === favorites) { ... }

// After — flag-based with microtask yield
let alreadyExists = false;
let updatedFavorites;
setFavorites(prev => {
  if (prev.some(fav => fav.id === product.id)) {
    alreadyExists = true;
    return prev;
  }
  updatedFavorites = [...prev, newFavorite];
  return updatedFavorites;
});
await Promise.resolve();
if (alreadyExists || !updatedFavorites) { ... }
```

Same pattern applied to `removeFromFavorites`.

**File changed:** `contexts/FavoritesContext.js`

### 4. `updateSize` stale `productOriginal` on repeated switches (HIGH)

**Problem:** When a user changed the size variant of a cart item, `updateSize` read `itemToUpdate.product.originalPrice` to determine if a server-confirmed discount existed. After the first size switch, this value was already an inferred value (computed from the user's discount percentage), not the server's raw original price. On the second switch, the code would infer again from the already-inferred value, potentially double-inflating the displayed retail price.

**Fix:** Instead of checking the stored product-level `originalPrice`, check whether **any variant** in the product's variant array has a server-set `originalPrice` (i.e., `originalPrice > price`). This is a stable check that doesn't depend on previously computed state.

```js
// Before — reads potentially-inferred value
const productOriginal = Number(itemToUpdate.product?.originalPrice);
const serverConfirmedDiscount =
  (Number.isFinite(variantOriginal) && variantOriginal > vp) ||
  (Number.isFinite(productOriginal) && productOriginal > 0);

// After — checks raw variant data
const anyVariantHasOriginal = variants.some((v) => {
  const vo = Number(v?.originalPrice);
  return Number.isFinite(vo) && vo > Number(v?.price);
});
const serverConfirmedDiscount =
  (Number.isFinite(variantOriginal) && variantOriginal > vp) ||
  anyVariantHasOriginal;
```

Also removed the fallback to `productOriginal` in `keptOriginal` computation since it could be stale.

**File changed:** `contexts/CartContext.js`

### 5. Hardcoded `/0.85` for Beauty Box `originalPrice` (MEDIUM)

**Problem:** The shop grid calculated a Beauty Box original price by dividing the display price by `0.85`, assuming a fixed 15% discount. This was fragile — if the discount percentage ever changed on the server, the displayed strikethrough price would be wrong.

**Fix:** Only show the strikethrough price if `product.originalPrice` actually exists from the server and is greater than the display price. If the server doesn't provide it, skip the strikethrough entirely.

```js
// Before — guesses original price
<Text style={styles.originalPrice}>
  {Number(product.originalPrice || ((price) / 0.85)).toFixed(2)} AED
</Text>

// After — only shows if server provided it
{Number(product.originalPrice) > Number(product.displayPrice || product.price || 0) && (
  <Text style={styles.originalPrice}>
    {Number(product.originalPrice).toFixed(2)} AED
  </Text>
)}
```

**File changed:** `app/(tabs)/shop.js`

### 6. `calculateCartTotals` called with wrong 4th argument (MEDIUM)

**Problem:** `checkout.js` called `calculateCartTotals(items, user, selectedEmirate, getAvailableEmirates())` — the 4th argument was a plain array of emirates. But `calculateCartTotals` expects a config object `{ emirates, freeShippingThreshold, vatRate }`. This caused `undefined` values for shipping thresholds and VAT rate, potentially leading to different totals between the bag screen and checkout screen.

**Fix:** Destructure `shippingRates` from `useCart()` and pass the correct config object:

```js
// Before
const totals = calculateCartTotals(items, user, selectedEmirate, getAvailableEmirates());

// After
const { ..., shippingRates } = useCart();
const totals = calculateCartTotals(items, user, selectedEmirate, {
  emirates: getAvailableEmirates(),
  freeShippingThreshold: shippingRates?.freeShippingThreshold,
  vatRate: shippingRates?.vatRate,
});
```

**File changed:** `app/checkout.js`

### 8. `splashVideo` initial state flicker in Expo Go (LOW)

**Problem:** `splashVideo` state starts as `null` and is resolved to either an object (with video config) or `false` (no video available). The Expo Go fallback check was `if (!splashVideo)`, which is truthy for both `null` (not yet resolved) and `false` (no video). This caused a brief flash of `BrandedLaunchScreen` before the video config loaded from cache.

**Fix:** Changed the check to `splashVideo === false` (strict equality) so it only triggers after resolution:

```js
// Before — triggers on null AND false
if (isExpoGo && showLaunch && !splashVideo) {

// After — only triggers after video config resolved to false
if (isExpoGo && showLaunch && splashVideo === false) {
```

**File changed:** `app/_layout.js`

### 9. Search filter effect missing `locale`/`t` deps (LOW)

**Problem:** The `useEffect` that filters products by `searchQuery` and `selectedCategory` only depended on `[searchQuery, selectedCategory, products]`. After a language switch, category names change (they're translated), but the filter wouldn't re-run to match the new translations.

**Fix:** Added `locale` and `t` to the dependency array:

```js
// Before
}, [searchQuery, selectedCategory, products]);

// After
}, [searchQuery, selectedCategory, products, locale, t]);
```

**File changed:** `app/(tabs)/shop.js`

### 10. `initialLoadDone.current` set before async completes (LOW)

**Problem:** The initial load effect set `initialLoadDone.current = true` synchronously, before `loadProducts()` and `loadCategories()` (both async) completed. The user-login effect checked this flag to decide whether to re-fetch products. If a user was already authenticated when the component mounted, the login effect could fire before the initial load finished, causing a duplicate API call.

**Fix:** Moved the flag assignment into a `.then()` callback after both async operations complete:

```js
// Before — flag set before data loads
useEffect(() => {
  loadProducts();
  loadCategories();
  initialLoadDone.current = true;
}, []);

// After — flag set after both resolve
useEffect(() => {
  Promise.all([loadProducts(), loadCategories()]).then(() => {
    initialLoadDone.current = true;
  });
}, []);
```

**File changed:** `app/(tabs)/shop.js`

### 12. `toggleFavorite` unhandled promise (LOW)

**Problem:** `handleToggleFavorite` called `toggleFavorite(product)` which returns a Promise, but didn't `await` it or attach a `.catch()`. If the async favorite toggle failed (network error, storage error), the error was silently swallowed.

**Fix:** Made the handler `async`, `await`ed the result, and wrapped in try/catch:

```js
// Before — fire and forget
const handleToggleFavorite = (product) => {
  haptics.lightTap();
  const result = toggleFavorite(product);
  ...
};

// After — awaited with error handling
const handleToggleFavorite = async (product) => {
  haptics.lightTap();
  try {
    const result = await toggleFavorite(product);
    ...
  } catch (err) {
    log.warn('toggleFavorite failed', err?.message || err);
  }
};
```

**File changed:** `app/(tabs)/shop.js`
